1. "Tree-Sitter AST parsing across 4 languages"

  • The Problem: Code is not like an English essay. If you chunk code by "every 50 lines", you might slice a function right in half, cutting off its variables or return statement.
  • What Tree-Sitter is: A fast, industrial grammar parser originally built by GitHub.
  • What an AST (Abstract Syntax Tree) is: It turns messy code text into a neat branching family tree of syntax nodes:

    File ⟶ Function Definition ⟶ Parameters, Body, Return

  • Across 4 languages: In your project (ast_parser.py), Tree-Sitter parses Python, Go, JavaScript, and TypeScript.
  • Why it matters: It guarantees that every chunk of code we send to our AI is a complete, self-contained function rather than broken lines.

2. "768-dimensional CodeBERT embeddings in ChromaDB"

  • What an Embedding is: Computers cannot do math on words. An embedding model turns a piece of code into a list of numbers (a vector coordinate).
  • What CodeBERT is: A Transformer neural network pre-trained by Microsoft on millions of code files. It outputs a list of exactly 768 decimal numbers for every function.
  • What ChromaDB is: A specialized Vector Database. Instead of searching by spelling like Google (A-Z), ChromaDB searches by mathematical distance:
    • If Developer A writes delete_user(uid) and Developer B writes remove_account(id), CodeBERT gives them nearly identical 768 coordinates because they mean the same thing!

3. "Fusing dense vector similarity with sparse BM25 retrieval"

Why do we need two different search engines?

  • Dense Vector Search (CodeBERT): Great at understanding intent and synonyms (remove ≈ delete), but sometimes misses exact variable names like MAX_RETRY_TIMEOUT_V2.
  • Sparse Search (BM25 / Keyword): Great at finding exact matching words and specific variable names, but completely blind to synonyms.
  • Hybrid Search: We run both at the same time so we get the best of both worlds: semantic understanding + exact keyword precision.

4. "via Reciprocal Rank Fusion (k=60)"

  • The Problem: You have two different search engines giving two different score types:
    • ChromaDB gives a Cosine Similarity score (e.g., 0.92).
    • BM25 gives a keyword frequency score (e.g., 14.8).
    • You cannot simply add 0.92 + 14.8—that would be like adding 5 kilometers to 20 pounds!
  • The Solution (RRF): Instead of adding their raw scores, you look at their rankings (1st place, 2nd place, 3rd place).
  • The Formula:

    $$RRF(d) = \sum_{m \in \{ ext{dense}, ext{sparse}\}} rac{1}{60 + ext{rank}_m(d)}$$

  • Why k=60?: 60 is the standard constant from research (Cormack et al.). It prevents an outlier ranked #1 in only one engine from unfairly dominating an item that ranked #2 in both engines.

5. "to enrich LLM prompts with codebase context"

  • This is the final payoff of RAG.
  • Instead of sending Groq/LLaMA an empty prompt:
    "Review this diff: [code]"
  • We send an enriched prompt:
    "Review this diff: [code].
    For reference, here are 2 functions already written in this repository that do something similar: [Function A, Function B].
    Make sure the new code follows the same patterns!"

  • How the Redis Queue Works:
    1. The Webhook Handler receives the notification, writes a tiny JSON job into a Redis List (review_jobs) using LPUSH, and immediately says "HTTP 200 OK" back to GitHub in 45 milliseconds.
    2. A separate background worker running in Go uses BRPOP (Blocking Right Pop) to gently pull jobs off the list one by one at its own comfortable pace.
  • Why it matters: Redis acts as an elastic shock absorber that decouples your fast front-end gateway from your heavier AI processing engine.
